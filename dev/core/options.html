Options#

The xtl_core.options module provides an API around pydantic.BaseModel that extends the existing validation and serialization capabilities in a user-friendly format. Options is a powerful data container that, in combination with Option(), can facilitate arbitrary validators and serializers in a slim syntax. This module is used internally to parse configuration from the xtl.toml file and to validate any modifications on the xtl.settings object.

Quickstart#

The module provides two objects: Option() and Options, which are wrappers around pydantic.Field() and pydantic.BaseModel, respectively. Below is a simple example that showcases what is possible with this API:

from pathlib import Path
from pydantic import Field
from xtl_core.options import Option, Options

class Employee(Options):
    name: str = Option(
        default=None,
        formatter=lambda x: x.title()
    )
    age: int = Field(
        default=None,
        gt=0
    )
    level: str = Option(
        default=None,
        choices=['junior', 'senior'],
        alias='job_level'
    )
    contract_file: Path = Option(
        default=None,
        cast_as=Path,
        path_exists=True,
        path_is_file=True
    )

employee = Employee(
    name='john doe',
    age=30,
    level='senior',
    contract_file='/path/to/contract.txt'
)

Now if we call employee.to_dict() (which is equivalent to employee.model_dump() if you prefer the Pydantic API), we get the following back:

>>> employee.to_dict()
{'name': 'John Doe',
'age': 30,
'contract_file': Path('/path/to/contract.txt'),
'job_level': 'senior'}

We notice a few things:

  1. The name attribute got formatted in title case (due to formatter), however the stored value is still 'john doe':

    >>> employee.name
'john doe'

    The formatter option only affects the serialization of the field.

  2. The age attribute was defined as a pydantic.Field() instead and it is still compatible with our model

  3. The level attribute was renamed to job_level (due to alias='job_level' which sets the serialization_alias on the Pydantic field), however the attribute is still accessible through its original name:

    >>> employee.level
'senior'
>>> employee.job_level
AttributeError: 'Employee' object has no attribute 'job_level'

    The alias option affects only model serialization.

  4. We checked whether the value for level is one of ['junior', 'senior'] (due to choices). If we try to change the value to something not in the list of choices we get a validation error:

    >>> employee.level = 'ceo'
pydantic_core._pydantic_core.ValidationError: 1 validation error for Employee
level
  Value error, Value is not in choices: ['junior', 'senior'] [type=value_error, input_value='ceo', input_type=str]

    Note

    The Options class has validate_assignment set to True.

  5. The contract_file was passed along as a str but is now Path (due to cast_as=Path, which performs type casting before Pydantic's model validation)

  6. We checked whether contract_file exists and whether it is a file (due to path_exists=True and path_is_file=True, which add custom Pydantic validators)

Data validation#

Pydantic comes with a variety of prebuilt validators that can be defined on the pydantic.Field() level. Option() provides support for all the existing Pydantic validators, plus a few extra ones. The complete list of validators is as follows:

  1. Numerical fields

    • gt: greater than

    • ge: greater than or equal to

    • lt: less than

    • le: less than or equal to

    • multiple_of: multiple of

    • allow_inf_nan: allow infinity or NaN values

  2. Decimal fields

    • max_digits: maximum number of digits

    • decimal_places: number of decimal places

    • all validators for numerical fields

  3. Iterable fields

    • length*: number of items in the iterable

    • min_length: minimum number of items in the iterable

    • max_length: maximum number of items in the iterable

  4. String fields

    • regex: regular expression

    • all validators for iterable fields

  5. Path fields

    • path_exists*: path exists

    • path_is_file*: path is a file

    • path_is_dir*: path is a directory

    • path_is_absolute*: path is absolute

  6. Enumeration fields

    • choices*: list of valid values

Validators marked with an asterisk (*) are implemented by XTL directly.

Type casting#

A special case of validator is generated when using the cast_as argument. This creates a pydantic.BeforeValidator that is called on the raw input data before any other validation is performed, and enables type casting.

Pydantic already performs type coercion on certain values by default, unless strict=True is explicitly set either on pydantic.Field() or pydantic.BaseModel. For example, in if a model field is defined as int, then passing a integer as str or as float will be coerced into type int:

from pydantic import BaseModel, Field

class CoercionModel(BaseModel):
    x: int = Field(default=None)

model = CoercionModel(x=1.0)
assert model.x == 1
assert isinstance(model.x, int)

model = CoercionModel(x='1')
assert model.x == 1
assert isinstance(model.x, int)

Details about Pydantic’s type coercion can be found in the documentation.

The cast_as argument provides some additional functionality, where it first checks if the value is of the correct type, and only attempts to type cast if not. An exemplary use case would be when an argument needs to be defined as a list[Any] but either a list or a single value could be passed:

 from xtl_core.options import Option, Options

 class CoercionModel(Options):
     x: list[str] = Option(default=None, cast_as=list)

 model = CoercionModel(x='1')
 assert model.x == ['1']
 assert isinstance(model.x, list)

 model = CoercionModel(x=['1'])
 assert model.x == ['1']
 assert isinstance(model.x, list)

Pydantic would have failed to coerce the value into a list in the first call.

Type casting is also useful when using custom types in models:

from xtl_core.options import Option, Options

class Animal:
    def __init__(self, species: str):
        self.species = species

class Pet(Options):
    animal: Animal = Option(default=None, cast_as=Animal)
    name: str = Option(default=None)

pet = Pet(animal='Tyrannosaurus rex', name='Otto')
assert isinstance(pet.animal, Animal)

Note

Options has arbitrary_types_allowed set to True.

Custom validation#

In Pydantic custom field validation can be done by defining methods that have been decorated with the @field_validator decorator. In Options this can additionally be achieved by passing a custom validation function to the validator argument of Option().

Any custom validation function should be first wrapped in a pydantic.BeforeValidator or pydantic.AfterValidator, depending on whether it should be run on the raw input data, or the already validated data.

from typing import Any
from pydantic import AfterValidator
from xtl_core.options import Option, Options

def is_odd(value: Any) -> Any:
    if value % 2 == 0:
        raise ValueError('Value must be odd')
    return value

IsOddValidator = AfterValidator(is_odd)

class OddNumber(Options):
    number: int = Option(default=None, validator=IsOddValidator)

number = OddNumber(number=4)
# raises pydantic_core._pydantic_core.ValidationError: 1 validation error for OddNumber
# number
#   Value error, Value is not odd [type=value_error, input_value=4, input_type=int]

Note the signature of the is_odd() function: It accepts a single argument, and returns it as is if the validation is passed, otherwise it raises a ValueError. Once all pydantic.AfterValidator have been executed, any ValueError that might have been raised will get aggregated into a single pydantic.ValidationError.

A few more important notes about crafting custom validators:

  • Value immutability: Options allows for validators to mutate the value. This is, for example, the case for the CastAsValidator which performs type casting. This ensure that the right value is propagated to the next validator. The model value is, however, only mutated from the input value if all validators succeed.

    Caution

    In general, validators should only check the value. Be very careful when mutating the value, as this can lead to unexpected behavior, for example in dictionaries.

    See also

    Mutating the value affects the way it is stored internally. If you find yourself crafting validators that change the way the value is output upon serialization, you should be creating a formatter instead (see: Data formatting)

  • Validation order: Validators are applied sequentially. The order of execution is as follows:

    1. Raw data received

    2. pydantic.BeforeValidator by XTL (if any)

    3. pydantic.BeforeValidator by user (if any)

    4. Pydantic's internal validation and model initialization logic

    5. pydantic.AfterValidator by XTL (if any)

    6. pydantic.AfterValidator by user (if any)

    7. Model instance is returned

Data formatting#

Once our model has been instantiated, we might want to pass all its data to another function, save it in a file, display it to the user, etc. Many times the way the data is stored inside the model and the way it is presented to the outside world have different requirements. In general, this concept is called serialization in Pydantic, and in XTL it can be controlled by the formatter and alias arguments in Option().

from pathlib import Path
from xtl_core.options import Option, Options

def PathUri(value: Path) -> str:
    return value.as_uri()

class Config(Options):
    a: int = Option(default=None, alias='param_a')
    b: str = Option(default=None, alias='param_b', formatter=lambda x: x.upper())
    file: Path = Option(default=None, formatter=PathUri)

>>> c = Config(a=1, b='value', file=Path('/path/to/file'))
>>> c.to_dict()
{'param_a': 1,
'param_b': 'VALUE',
'file': 'file:///path/to/file'}

Model I/O#

Options models can be serialized to and deserialized from Python dictionaries, JSON and TOML files and/or strings. There are aptly named methods (from_*/to_*) for each purpose.

from xtl_core.options import Option, Options

class NestedModel(Options):
    a: int = Option(default=None, formatter=lambda x: 10 * x,
                    desc='This is 10 times the original')

class ParentModel(Options):
    b: float = Option(default=None, alias='c',
                      desc='This is an aliased value')
    nested: NestedModel = Option(default_factory=NestedModel)

p = ParentModel.from_dict({'c': 3., 'nested': {'a': 2}})
p.to_toml('output.toml', comments=True)

This will output an output.toml file, which will include all the field descriptions as inline comments to the values.

output.toml#
c = 3.0 # This is an aliased value

[nested]
a = 20 # This is 10 times the original

Fields left unset#

TOML has no null, so a field set to None is left out of a TOML file, and loads as its default. For a field that should be left out of every output while it isn’t set, use Pydantic's MISSING sentinel as its default. A field holding MISSING is left out of to_dict(), to_json() and to_toml(), and is MISSING again once loaded; validators and formatters skip it, and assigning MISSING unsets the field. None then remains a value of its own.

from pydantic import MISSING
from xtl_core.options import Option, Options

class Config(Options):
    limit: int | None | MISSING = Option(default=MISSING, gt=0,
                                         desc='Maximum number of items, or None for no limit')

>>> Config().to_dict()
{}
>>> Config(limit=None).to_dict()
{'limit': None}
>>> Config.from_dict({}).limit
MISSING

Note

MISSING is for a field’s own value: inside a list or a dictionary it can’t be written to JSON or TOML. It is also truthy, so check it with value is MISSING, not if value:. Data can’t set it either: 'MISSING' in a file is an ordinary string.

Environment variables#

Options also support parsing of environment variables on string fields. Due to safety considerations, this behaviour is disabled by default. To enable environment variable parsing, you need to pass _parse_env=True during model instantiation. Any strings that contain expressions in the form of ${VARIABLE} will be replaced by the value of the respective environment variable.

import os
from xtl_core.options import Option, Options

class Settings(Options):
    a: str = Option(default=None)

>>> os.environ['SECRET'] = 'alakazam'
>>> Settings(a='secret is ${SECRET}').to_dict()
{'a': 'secret is ${SECRET}'}
>>> Settings(a='secret is ${SECRET}', _parse_env=True).to_dict()
{'a': 'secret is alakazam'}

If an environment variable is not set, then the content will be replaced with an empty string. The parsing of environment variables is a mutable operation, meaning that the value of the field is replaced with that of the variable. Changing the environment variable after model instantiation will have no effect on the field’s value, unless the same expression is reassigned to the field, and the model undergoes validation again.

Important

The _parse_env argument is only local in scope, meaning that it only applies to the current model. In case of nested Options models, environment variable parsing will not be propagated from the parent model to its childs.

Versioned data#

Models that are saved to files, such as configuration or records, tend to change over time: a field gets renamed, a new one is added, or one is split into two. VersionedOptions is an Options model whose data carries a version tag, so that files saved with an older layout are upgraded to the current one when they are loaded, one version at a time. The version tag belongs to the model’s data layout, not to xtl: it only changes when the layout does.

Declaring a model#

A versioned model sets three class variables: where the version tag lives in the data (_version_path, a dot-separated path such as 'version' or 'metadata.version'), the current version of the layout (_current_version), and the module that holds the upgrade steps (_upgrades). The version field itself is an ordinary field whose default is the current version, so that saved data always carries it.

hr/models.py#
from xtl_core.options import Option, VersionedOptions

class Employee(VersionedOptions):
    _version_path = 'version'
    _current_version = '3.0.0'
    _upgrades = 'hr._upgrades'

    version: str = Option(default='3.0.0', desc='Layout version of the record')
    first_name: str = Option(default=None)
    last_name: str = Option(default=None)
    level: str = Option(default='junior', choices=['junior', 'senior'], alias='job_level')

Versions are written as 'X.Y.Z' strings (or VersionInfo objects) and are compared on their major, minor and micro parts only, so '2.0.0.dev0' counts as '2.0.0'.

Writing upgrade steps#

Each change to the layout gets an upgrade step: a function that takes the data in the old layout as a plain dictionary, and returns it in the new one. Steps are registered on the model with upgrade_step(), keyed by the version they upgrade to. Versions don’t need to be consecutive.

Suppose that version 1.0.0 of the employee records stored name and position, version 2.0.0 renamed position to job_level, and version 3.0.0 split name into first_name and last_name:

hr/_upgrades.py#
from xtl_core.options import Option, Options
from hr.models import Employee

@Employee.upgrade_step(to='2.0.0')
def _rename_position(data: dict) -> dict:
    data['job_level'] = data.pop('position')
    return data

class EmployeeV2(Options):
    """The 2.0.0 layout of Employee, frozen."""
    version: str = Option(default='2.0.0')
    name: str = Option(default=None)
    level: str = Option(default='junior', alias='job_level')

@Employee.upgrade_step(to='3.0.0', model=EmployeeV2)
def _split_name(old: EmployeeV2) -> dict:
    first_name, _, last_name = old.name.partition(' ')
    return {'version': old.version, 'first_name': first_name, 'last_name': last_name,
            'job_level': old.level}

The first step works on the raw dictionary, which is enough for most changes. The second is a typed step: with model=EmployeeV2, the data is first validated as a frozen copy of the old layout, and the step gets an EmployeeV2 instance instead of a dictionary. This is worth it for bigger changes, where attribute access and validation of the old data help. The frozen model is a plain Options, not a VersionedOptions.

Keeping the steps in a module of their own has two benefits: the module is only imported the first time old data is upgraded, so loading up-to-date data costs nothing extra, and it can import the model (and its frozen copies) without circular imports.

Note

The steps don’t need to set the version tag: it is updated after each step, so that each step sees the version it upgrades from, and it is set to the current version at the end.

Loading data#

Upgrades happen automatically in from_dict(), from_json() and from_toml(). Given a john.json file saved with version 1.0.0:

john.json#
{"version": "1.0.0", "name": "John Doe", "position": "senior"}

both steps run, in order, and the result is validated as the current model:

>>> Employee.from_json('john.json')
Employee(version='3.0.0', first_name='John', last_name='Doe', level='senior')

The file itself is not changed. To save it in the new layout, write it back:

>>> Employee.from_json('john.json').to_json('john.json', overwrite=True)

For a TOML file that people edit by hand, upgrade_toml() keeps its comments and formatting: it takes the text, edits only what the steps changed (renamed or removed keys, changed values, which keep their inline comment) and sets the version, and returns the new text. New keys get their field’s description as a comment. clean=True writes the upgraded data afresh instead, as to_toml(comments=True) does, and add_missing=True also adds the fields that the text doesn’t have (fields without a TOML value as commented-out lines, # key = ...):

>>> from pathlib import Path
>>> path = Path('john.toml')
>>> path.write_text(Employee.upgrade_toml(path.read_text()))

If you only need the upgraded data, upgrade() returns it as a dictionary, without validating it (the input is left unchanged):

>>> Employee.upgrade({'version': '1.0.0', 'name': 'John Doe', 'position': 'senior'})
{'version': '3.0.0', 'first_name': 'John', 'last_name': 'Doe', 'job_level': 'senior'}

Passing upgrade=False to any of the loaders skips the steps and validates the data as it is, which for an old file usually fails:

>>> Employee.from_json('john.json', upgrade=False)
xtl_core.options.exceptions.OptionsValidationError: 2 validation errors for Employee
  Employee.first_name
    Input should be a valid string [type=string_type, input_value=None, input_type=NoneType]
  ...

Two more cases load without any upgrade:

  • Data from a newer version than the model’s (e.g. a file written by a newer xtl) is validated as it is, with a warning in the log:

    WARNING:xtl_core.options.versioned:Employee data is from version 4.0.0, which is newer than the model's current version 3.0.0.

  • Data without a version (e.g. a file written by hand) is treated as current: no steps run, and the version field takes its default.

Subclasses#

A subclass of a versioned model shares its version tag and runs its parent’s upgrade steps, since its data contains the parent’s fields:

class Manager(Employee):
    reports: list[str] = Option(default_factory=list)

>>> Manager.from_dict({'version': '1.0.0', 'name': 'Ann Lee', 'position': 'senior',
...                    'reports': ['John Doe']})
Manager(version='3.0.0', first_name='Ann', last_name='Lee', level='senior', reports=['John Doe'])

reports survives the typed step _split_name, even though EmployeeV2 doesn’t know about it: a typed step’s frozen model only gets the keys it knows, and the other top-level keys are carried over into the step’s result (unless the step sets them itself).

A subclass can register upgrade steps of its own, with @Manager.upgrade_step(...) in an _upgrades module of its own. To change its own layout, it raises _current_version (e.g. to '3.1.0') and adds a step to that version. For steps to the same version, the parent’s run first. A subclass can’t lower _current_version below its parent’s, nor move the version tag to another _version_path: both raise a TypeError when the class is defined.

Important

Fields that a subclass adds inside a nested section of its parent are not carried over by the parent’s typed steps; only top-level keys are. If a parent’s typed step rewrites a section that a subclass extends, the subclass needs a step of its own for that section.
