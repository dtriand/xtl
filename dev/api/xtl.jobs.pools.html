class xtl.jobs.pools.AsyncPool[source]#

Bases: BasePool

A pool for running jobs asynchronously. The jobs are executed within the same process and same thread (and event loop). This is well suited for running I/O-bound task, e.g. fetching data over network, executing batch jobs. It is the most responsive pool type, since it does not add any IPC overhead.

class xtl.jobs.pools.BasePool[source]#

Bases: PoolProtocol, ABC

__init__(name=None, max_jobs=1, logger_config=None, resources=None, resources_manager=None, parent_logger=None, **kwargs)[source]#

Abstract base class for job pools.

The pool’s logger is the root of a tree: the jobs’ loggers are its children (<pool logger>.<job_id>), and steps hang under their job. Jobs’ loggers have no handlers and propagate, so that the pool’s handlers get every record. The pool’s logger doesn’t propagate further.

Parameters:

  • name (str | None) – Optional name for pool; it can’t contain dots or #

  • max_jobs (int) – The maximum number of concurrent jobs to run. This is capped by the available quota (default: 1).

  • logger_config (LoggerConfig) – Optional configuration for the pool’s logger.

  • resources (Resources | None) – Optional resources to request for this pool. This is capped by the available quota (default: None, get all available)

  • resources_manager (ResourceManager | None) – Optional ResourceManager to use for resource allocation. If not provided, the default global ResourceManager will be used.

  • parent_logger (Logger | None) – Optional, the logger of the job that creates this pool. The pool’s logger then hangs under it and passes its records up, with no handlers of its own, unless a logger_config is passed.

  • kwargs – Additional keyword arguments.

Raises:

  • ValueError – If an invalid max_jobs is provided, or if name contains dots or #

  • TypeError – If logger_config is not of the correct type

add_job_handler(spec, name)[source]#

Give every job submitted from now on its own handler, built from spec where the job runs, attached to the job’s logger while it runs, and closed before its directory is cleaned up. String fields of the spec (except its format) and string values of its options may hold placeholders that each job fills in: {job_directory}, {job_id}, {job_class} and {pool} (this pool’s label). A job’s config can replace the spec, or switch it off, by its name (JobConfig.log_handlers).

Example:

pool.add_job_handler(JobFileHandlerConfig(), name='file')  # `<job_directory>/xtl.log`
Parameters:

  • spec (HandlerConfig) – The handler’s config. It travels with each job, so it must survive JSON.

  • name (str) – The spec’s name; a second spec with the same name replaces the first.

Return type:

None

get_state(name)[source]#

Get a shared state dict from the pool. If the requested state does not exist, it will be created. Per-operation atomicity is guaranteed. Any compound read-modify-write (RMW) operations (e.g. in-place modification) are NOT atomic and must be protected with an explicit lock.

Example usage:

state = pool.get_state('my_state')
# Atomic operation
state['counter'] = 0
# Compound RMW - unsafe
state['counter'] += 1  # 3 separate operations: get, modify, set - not atomic!
# Compound RMW - safe with lock
async with pool.get_lock():
    state['counter'] += 1  # Protected by lock, safe to perform compound RMW
Parameters:

name (str) – The name of the state to retrieve.

Raises:

RuntimeError – If the pool is not currently active (i.e., not within the context manager).

Returns:

An IPCState instance corresponding to the requested state.

Return type:

IPCState

submit(job_cls, configs=None, *, job_ids=None)[source]#

Submit a job to the pool for execution. This method must be called from within the pool’s context manager.

Example:

async with pool:
    pool.submit(MyJob, configs=[config1, config2])
    results = pool.launch()
Parameters:

  • job_cls (Type[Job]) – The job type to submit. Must be a subclass of Job.

  • configs (JobConfig | None | Iterable[JobConfig | None]) – The configs to submit to the pool.

  • job_ids (Iterable[str | None] | None) – Optional, the IDs of the submitted jobs, one per config (None for a random one). If not provided, IDs are generated as <job_cls>-<i>, where i is an incrementing index; such a job is shown as <job_cls>|<i> (its label). Given IDs must be usable in file names and commands (no | / \ : * ? " < >).

Raises:

  • RuntimeError – If the method is called outside the pool’s context manager

  • TypeError – If job_cls is not a subclass of Job.

  • TypeError – If one of the configs is not a JobConfig instance or None.

  • ValueError – If job_ids is provided but does not have the same length as configs

  • ValueError – If a job id is already in the pool, given twice, or not usable in file names and commands

Returns:

A list of the configured submitted jobs.

Return type:

list[Job]

class xtl.jobs.pools.MultiprocessPool[source]#

Bases: BasePool

A pool for running jobs in separate processes. This pool is well suited for running CPU-bound tasks, e.g. heavy numerical calculations. It can also be used to impose stronger isolation between worker processes. It has the highest overhead among the pool types upon initialization. Internally, the spawned subprocesses are managed by a ProcessPoolExecutor.

class xtl.jobs.pools.SimplePool[source]#

Bases: AsyncPool

A pool for running jobs synchronously. This is a thin wrapper around AsyncPool, that enforces a sequential job execution (max_jobs=1). Suitable for running a single job, or when concurrency is risky. It can also be used for debugging, since it enforces a deterministic operations order.

class xtl.jobs.pools.ThreadedPool[source]#

Bases: BasePool

A pool for running jobs in separate threads. The jobs are executed within the same process but in separate threads. This pool is well suited for running I/O-blocking tasks, e.g. non-async APIs, filesystem I/O. Not ideal for CPU-bound tasks, since Python (at least < 3.14) is not truly threaded. Internally, the spawned threads are managed by a ThreadPoolExecutor.
